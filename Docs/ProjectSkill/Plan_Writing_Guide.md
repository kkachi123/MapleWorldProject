# 계획 문서 작성 원칙

## 1. 명확한 목표와 범위

- 완료 후 관찰할 수 있는 동작을 1~2문장으로 설명한다.
- 포함·제외 범위를 구분하고 요청받지 않은 기능을 추가하지 않는다.
- 승인된 요구, 제안, 가정, 미확정 사항을 구분한다. 승인된 계획과 구현 착수 승인을 혼동하지 않는다.
- 기존 기능을 바꾸면 현재 처리와 필요한 차이를 짧게 적는다. 변경 이유가 없는 기존 구조 설명은 반복하지 않는다.
- 결과를 바꾸는 미결정 사항만 질문 대상으로 남긴다. 결정되지 않은 수치를 확정값처럼 쓰지 않는다.

## 2. 구현 가능한 단계와 확인 기준

- 단계는 의존성·실행 순서가 보이게 작성하고 각 단계의 산출물을 명시한다.
- 대상 파일·책임·데이터·권한·수명·중단 조건 등 구현에 필요한 경계를 작업 규모에 맞게 적는다.
- 필요한 범위보다 큰 프레임워크·미래 기능을 미리 설계하지 않는다.
- 성공 기준은 ‘정상 동작’ 대신 어떤 조건에서 무엇이 관찰돼야 하는지 쓴다.
- 정상 흐름·오류/중단 조건·기존 기능 영향의 확인 방법을 구분한다. 자동 검사와 사람이 직접 판단할 조건도 구분한다.
- 필요한 환경·데이터·도구가 없으면 선행 조건으로 표시한다. 실행할 수 없는 검증을 완료 기준에서 숨기지 않는다.

## 3. 기본 작성 틀

작업에 필요한 항목만 사용하고 안내 문구는 제거한다.

```markdown
# {작업명} 계획

## 목표·상태
{완료 후 동작과 제안/승인/진행 상태}

## 범위
- 포함: {대상·기능}
- 제외: {이번에 하지 않을 일}
- 미확정·의존성: {필요할 때만}

## 예정 처리
{현재와의 차이·필수 책임/계약/제약}

## 실행 단계
- [ ] {작업과 산출물}
- [ ] {다음 작업과 산출물}

## 확인 기준
- {조건·방법·기대 결과}
- {중단·실패·회귀 조건}
```

## 4. 검토·갱신 원칙

- 현재 동작, 예정 설계, 실제 구현, 확인 완료를 구분한다.
- 미착수·구현 후 확인 대기·완료·보류 상태가 무엇을 뜻하는지 일관되게 사용한다.
- 실제 진행으로 범위가 바뀌면 해당 요구·의존성·완료 기준을 함께 정리한다. 미실시를 통과로 바꾸지 않는다.
- 계획 본문은 최종 승인 방향으로 정돈한다. 폐기한 설계·실패 로그·변경 회차를 계속 누적하지 않는다.
- 이미 존재하는 상세 자료는 참조하고 필요한 차이만 쓴다. 전체 코드·긴 의사 코드·반복 체크리스트는 줄인다.
- 간결함 때문에 필수 조건을 생략하지 않는다. 다른 담당자가 계획만으로 작업 범위와 성공 조건을 이해할 수 있어야 한다.
