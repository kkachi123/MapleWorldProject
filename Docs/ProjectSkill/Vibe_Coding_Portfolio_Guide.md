# 바이브 코딩 포트폴리오 제작 원칙

## 1. 목적·독자·범위

- 지원 목적·독자·발표/제출 형식에 맞춰 사례와 분량을 정한다. 조건이 미정이면 미정으로 두고 임의로 확정하지 않는다.
- 기능을 모두 나열하기보다 본인의 역할·판단·행동과 확인된 결과가 연결되는 사례를 선정한다.
- 프로젝트 전체 결과와 본인이 기여한 범위를 분리한다. 팀 결과를 개인 성과로 바꾸지 않는다.
- 기획·구현·검증·출시의 어느 단계까지 완료됐는지 명확히 적는다.

## 2. 본인 기여와 AI·외부 기여

- 본인이 실제 수행한 요구 정의·선택·제작·검토·플레이 평가만 개인 기여로 쓴다. 직접 한 근거가 없는 업무는 추정하지 않는다.
- 본인이 선택 이유를 설명하지 않았다면 이유를 창작하지 않는다. 타인의 제안을 채택한 사실과 직접 설계한 사실을 구분한다.
- AI가 작성한 코드·원인 분석·버그 수정·자동 검증을 본인이 수행한 기술 문제 해결로 표현하지 않는다.
- AI 활용 제작은 ‘제작 의도 → 본인 요구·선택 → 직접 평가·수정 요청 → 반영된 결과’로 설명할 수 있다. 모든 프롬프트나 AI 시행착오를 본문에 싣지 않는다.
- 엔진 기본 기능·패키지·에셋·공동 작업자·외부 자료의 사용과 기여를 명시한다.
- 본인이 이해하고 설명할 수 있는 범위만 소개한다. 학습해 설명할 수 있다는 사실을 직접 구현했다는 의미로 바꾸지 않는다.

## 3. 주장과 근거

| 주장 | 필요한 근거 |
| --- | --- |
| 무엇을 요구·선택·평가했다 | 본인의 작성물·결정·직접 관찰 |
| 어떤 기능이 구현됐다 | 대상 버전의 소스·설정·실제 결과물 |
| 동작을 확인했다 | 주체·환경·절차·기대/실제 결과 |
| 결함을 해결했다 | 재현 조건·수정과 전후 확인, 실제 수행자 |
| 성능이 개선됐다 | 동일 조건·지표/단위·횟수·전후 실측값 |

- 구현 예정·구현됨·자동 검증·본인 직접 확인을 구분한다. 미실행·미측정·가설은 명시한다.
- 다른 사람이 수행한 검사와 본인의 관찰을 바꾸어 쓰지 않는다. 코드 리뷰만 했으면 실제 실행 검사로 표현하지 않는다.
- 캡처·영상·로그·소스는 각각 입증 가능한 범위 안에서 사용한다. 대상 버전·시점·환경을 식별하고, 원시 근거가 없으면 요약만 남았다고 밝힌다.
- 측정 없는 개선율·메모리 누수 해소·모든 환경의 품질 보장을 주장하지 않는다.
- 공개 자료에서 비밀 키·개인정보·식별자를 제거하고 외부 자료의 출처·사용 조건을 확인한다.

## 4. 문서·발표 구성

1. 프로젝트 소개: 목표 경험·현재 완성 범위·대표 장면.
2. 본인 역할: 직접 맡은 책임과 AI·팀·엔진·외부 자료의 범위.
3. 대표 사례: 본인의 의도·결정/행동과 결과가 연결되는 사례.
4. 결과·한계: 확인한 결과와 미완성·미확인 부분.
5. 부록: 질문에 필요한 상세 근거·관련 자료.

사례는 다음 틀을 필요에 맞게 사용한다.

```markdown
## {사례의 핵심}

- 의도·요구: {본인이 만들고자 한 것}
- 본인 결정·행동: {실제 수행한 선택·제작·평가}
- 반영 결과: {확인된 결과와 범위}
- 역할 구분: {본인 / AI / 팀·엔진·외부 자료}
- 시각 자료·근거: {실제 확보한 자료}
- 한계: {미확인 조건·추가로 필요한 확인}
```

기술 분석·수정이 본인 수행인 경우에만 개인 기술 문제 해결 사례로 구성한다. 한 화면에는 하나의 핵심 주장을 두고, 긴 코드·전체 검증표·개발 일지는 근거 자료로 분리한다. 존재하지 않는 시연·측정값·개발 기간을 채우지 않는다.

## 5. 제작 후 점검

- 본인 기여와 다른 수행자의 기여가 명확한가?
- 예정 기능을 완료 성과로 소개하거나 선택 이유를 꾸미지 않았는가?
- 핵심 주장과 근거의 버전·환경·확인 주체가 일치하는가?
- 문서의 기능 설명을 옮긴 것에 그치지 않고 본인의 역할과 판단이 드러나는가?
- 출력·제출 파일의 글자·도식·영상·링크를 확인했는가?
- 발표가 있다면 시간을 실제로 재고, 시연 순서·실패 시 대체 자료·예상 질문을 준비했는가?
