# Project StayCool — 개발 단계 로드맵

> 기준일: 2026-10-20(현황 갱신 2026-11-02, 단계 구조 갱신 2026-11-03). 상위 기획은 [GameDesign](GameDesign.md)이며, 이 문서는 개발 순서·단계별 목표·완료 기준을 정의한다. 문서 작성은 신규 기능 구현이나 검증 완료를 의미하지 않는다.

## 1. 개발 기준

- 기존 전투 프로토타입 안정화는 종결됐다. 기존 전투 기반을 유지하며 기획 기능을 순서대로 개발하며, 전면 리팩토링을 다시 시작하지 않는다.
- 첫 목표는 **몬스터 1종·기본 스킬 1개로 기획에 맞는 전투 한 방을 완성하는 것**이다. 이후 Run·성장·콘텐츠를 연결한다.
- 1인 전용이며 각 전투는 플레이어 1명과 현재 상대 몬스터 1개체의 1:1 대결이다. PC·모바일 가로 화면 공통이며 현재 MapleTile(`TileMapMode=0`) 기반을 유지한다.
- 입력 정책은 확정됐다. 먼저 수락한 한 동작만 실행하고, 다른 동작은 무시한다. 입력 예약·동작 취소를 추가하지 않는다. 동일 홀드는 출처별로 합산하고 마지막 해제 때 종료한다.
- 공격은 ↑/W·기존 공격 버튼으로만 실행한다. 저스트 회피·패링 성공은 자동 공격이 아니라 후속 공격의 피해 증가 기회를 제공한다. 별도 반격 버튼·동작은 만들지 않는다.
- 저스트 회피는 몬스터 슬로우, 패링은 그로기로 연결한다. 판정 수치는 DataSet에서 조절하고 이후 스킬·스탯 보정을 적용할 수 있게 한다.
- 단계 구조(2026-11-03 사용자 확정): 1~7단계는 기초 확립이다. 시스템을 구현하고, 시스템별 DataSet 표 구조(열)를 확정하고, 1번 마을(헤네시스)을 표준 견본으로 완성·검증한다. 8단계는 확정된 표 구조에 콘텐츠 행을 채우고, 9단계에서 출시를 검증한다.
- 확장 원칙(2026-11-03 사용자 확정): 마을은 지속적으로 출시할 수 있는 것을 목표로 한다. 마을 수에 상한이 없는 누적 구조이며, 마을 수·해금 조건·표 구성은 나중에 계속 추가할 수 있게 유지한다. "첫 출시 범위"는 최종 마을 수가 아니라 8단계를 몇 번 마을까지 채운 뒤 9단계로 갈지 정하는 컷라인이다. 첫 출시 뒤에도 8단계 제작 → 9단계 필수 확인을 반복해 마을을 이어 붙인다(§3의 9). 아래 세 방향은 이 요청을 구조로 옮긴 것이며 열 이름·조건 값은 미정이다.
  - 마을: 마을 목록·순서·해금 조건을 DataSet 행으로 둔다. 새 마을은 행 하나를 추가해 반영한다. 해금 조건도 유형을 늘릴 수 있는 형태(예: 조건 유형 열 + 값 열)로 둔다. 표 구조는 6단계 헤네시스 견본에서 마련하고, 조건 값은 [8단계 시작 전 결정 사항](#8-콘텐츠-데이터-제작)에서 정한다.
  - 표 구성: 1~6단계에서 확정한 표 구조(열)는 고정이 아니며 이후에도 열을 추가할 수 있다. 추가한 열은 기존 행이 깨지지 않게 기본값을 둔다(빈 칸이면 기본값으로 처리). 기존 열의 의미 변경·이름 변경·삭제는 기존 마을 영향과 함께 사용자 판단을 받는다.
  - 코드·저장 요건(2026-11-04 사용자 확정, 메인 제안에서 승격): 마을 수·목록을 코드에 하드코딩하지 않고, 마을 선택 화면은 마을이 N개로 늘어도 동작한다(6단계 완료 기준). DataStorage는 마을·Stage를 순번이나 개수가 아닌 고유 id 기준으로 기록해, 마을이나 열을 추가해도 기존 저장이 깨지지 않게 한다(5단계 완료 기준).
- 데이터 원칙: DataSet은 모든 플레이어가 함께 쓰는 정적 데이터다(예: 강화 비용·몬스터 능력치·드롭 확률). 플레이어별 성장 결과(예: 강화 단계·보유 메소)는 DataStorage에 두며 5단계에서 연결한다. 두 저장소를 "DB"라는 한 말로 섞지 않는다. 최종 능력치 = DataSet 기본값 + 강화 보정이다.
- 에셋 원칙(2026-11-03 사용자 확인): 몬스터 외 에셋(배경·맵, NPC, 장비·아이템 아이콘, UI 이미지, 이펙트·사운드 등)은 1~7단계에서 각 시스템을 만들 때 헤네시스 기준으로 MSW 리소스(msw-search)에서 찾는다. 8단계에서는 마을마다 같은 종류를 찾는다. 적합한 리소스가 없으면 사용자 제공 또는 msw-painter 직접 제작 중 무엇으로 할지 사용자에게 묻고, 임의로 대체하지 않는다.
- 에셋 목록: 임시·대체 에셋을 추적하는 목록을 둔다. 위치는 `Engineering/AssetList.md`를 제안한다(planner 제안, 2026-11-05 회차 C Plan에서 [잠정 작성](AssetList.md)). 첫 에셋 작업 회차([Plan §18](Plans/2_CombatCore.md) 머쉬맘 전환)에서 이 위치에 잠정으로 만들고, 최종 위치는 [8단계 시작 전 결정 사항](#8-콘텐츠-데이터-제작)에서 확정하며 필요하면 그때 옮긴다. 각 항목에 용도·현재 RUID·임시 여부·확정 조건을 적는다. 현재 머쉬맘이 쓰는 주황버섯 리소스처럼 이미 알려진 임시 에셋도 이 목록에 올린다.
- 프로토타입 자동 반격은 2단계에서 제거하고 수동 공격 보너스로 바꿨다. 구현·독립 QA·리뷰 근거는 [CombatCore Plan](Plans/2_CombatCore.md)을 따르며 사용자 V11 확인 전이다. 1단계 이동·입력은 기존 AI 확인과 2026-10-20 사용자 V08 확인 완료 보고로 종료했다.

## 2. 개발 순서

이전에 정한 1~6단계 순서를 유지하고, 승인된 전투 일시정지를 0단계 선행 작업으로 둔다. 2026-11-03 사용자 확정으로 7단계를 헤네시스 기준 기초 완성도 검증으로 좁히고, 8단계 콘텐츠 데이터 제작과 9단계 출시 검증을 추가했다. 기존 7단계의 출시 관련 완료 기준은 9단계로 옮겼다. UI는 각 기능과 함께 개발하며, 7·9단계에서 통합 완성도를 확인한다.

| 9. 출시 검증 | 선행: 첫 출시 범위 콘텐츠 완성(컷라인까지 8단계 완료). 출시 대상 전체 콘텐츠 기준 PC·모바일 가로 화면, 연출·사운드·밸런스·성능, 저장 오류·배포 환경·장시간 반복 플레이 | 출시 대상 전체 콘텐츠로 실제 기기·배포 환경에서 성공·실패·재도전·재접속을 확인하고, 장시간 반복 플레이와 공개 전 필수 결함을 해소한다. 미측정 성능·미실시 환경은 통과로 처리하지 않는다. 출시 결정은 사용자가 한다 |

## 3. 단계별 선행 조건과 결정 시점

### 0 → 1: 정지·재개 계약을 먼저 고정

- 현재 맵의 전투 일시정지 구현·Maker 자동 검증은 [CombatPause 완료 기록](Features/0_CombatPause.md)에 정리했다. 사용자 승인으로 실제 맵 전환·PC/모바일 화면·음향은 [후속 검증 계획](Plans/CombatPause.md)에 남겼다. 이를 모든 환경의 검증 완료로 보지 않는다.
- 일시정지는 동작 취소가 아니다. 다음 단계의 보간 이동·슬로우·그로기도 같은 전투 시간과 종료 우선순위를 따라야 한다.
- 이 문서에서는 기존 계획의 검증 ID·세부 진행 상태를 복제하거나 완료로 변경하지 않는다.

### 1: 이동 수치와 복귀 표현

- 확정된 입력 정책을 다시 설계하지 않는다. 현재 보간 이동·중앙 복귀 속도와 걷기/대기 전환은 [MovementInput 완료 기록](Features/1_MovementInput.md)을 따른다. 사용자 V08 수락 당시 이동·복귀 속도는 각각 6이며 개별 기기·수치별 평가를 추정하지 않는다.
- 방 진입의 암전 중 `BattlePos2` 즉시 배치와 전투 중 보간 이동을 구분한다.

### 2: 전투 판정·데이터 계약

- 현재 상세 계획은 [CombatCore](Plans/2_CombatCore.md)다. 2026-10-20 사용자가 D01~D04를 결정했다. P01a 규칙 확정·문서 동기화는 완료했다. P01b~P06은 구현·coder 기본 검증·독립 QA·독립 리뷰를 거쳤으며 사용자 V11 확인이 남아 🟡다. 진행 근거는 Plan과 [WorkRecord](WorkRecords/CombatCoreWorkRecord.md)를 따른다.
- 일반은 가드/방향 회피, 특수는 가드·패링 불가, 패링 속성은 유효 저스트/패링 성공과 실패 가드 경감을 구분한다. 저스트/패링 창 0.20초, 가드 잔여 피해 40%, 성공 피해 0을 확정했다.
- 2026-11-03 사용자 결정(V11-F06): 주황버섯은 2칸(뒤·앞 회피형)과 1칸(방향 무관 회피형) 공격만 쓰고, 3칸 가드형은 보스용으로 유지한다. 출현 비율은 패턴 DataSet 가중치로 정한다. 몬스터 수치 DataSet화(V11-F07)는 V11 종료 뒤 별도 승인 회차에서 다룬다.
- 2026-11-03 사용자 V11 결과 뒤 결정(V11-F10·F11·REV-F02): 주황버섯은 보라 2칸 좌·우, 보라 1칸 최근접, 특수 1칸 무작위 칸(비중 약 1/7)만 쓴다. 특수 가드 결과는 "가드 불가"로 표시하며 규칙은 유지한다. 몬스터 사망 시 die 모습을 2단계에서 고정한다. 그 뒤의 암전·다음 Stage 전환은 4단계에서 연결한다.
- 2026-11-03 사용자 V11 결과 뒤 확정(회차 A, [Plan §19](Plans/2_CombatCore.md), 2026-11-04 구현 지시): die는 한 번만 재생하고 끝 모습에서 멈춘다(V11-F12). 저스트 회피·패링은 입력 시작 위치가 2번 칸이고 공격 범위가 2번 칸을 포함할 때만 성공한다(V11-F13). 끝 칸 1칸 공격에는 저스트·패링 보상이 없다. 수치는 바꾸지 않는다.
- 2026-11-03 사용자 설명·결정: 현재 전투 상대는 1번 마을(헤네시스) Stage 10 최종보스 머쉬맘이다. 위 결정의 "주황버섯"은 머쉬맘을 뜻하며, 현재 구현은 주황버섯 리소스를 쓴다. 실제 머쉬맘 리소스 교체와 이름 변경은 [Plan §18](Plans/2_CombatCore.md)의 다음 회차 후보로, §17 회차와 분리한다.
- 모든 유효 저스트/패링 성공 후 2.0초 동안 다음 직접 공격 1회 전체 타격 ×2.2. 유효 시전 시작에 소비하고 빗나가도 소비한다. 슬로우 2.0초×0.5와 그로기 1.5초는 유일한 현재 대결 상대에게만 적용한다. 그로기는 패링 뒤 처음 위치로 복귀한 다음 시작한다(2026-11-02 사용자 변경). 상세 시간·소비·중단 경계는 원본 Plan을 따른다.
- 기존 현재 상대 참조의 단일 소유권을 사용하고 범용 몬스터 집합·다중 대상 전투 체계를 앞당겨 만들지 않는다.
- DataSet 기본값과 스킬·스탯 보정의 책임을 분리한다. 이후 성장을 연결할 경계만 마련하고 성장 시스템 전체를 앞당겨 구현하지 않는다.
- 2단계 회차 B([Plan §20](Plans/2_CombatCore.md), 2026-11-04 사용자 "기본안으로 시작"으로 구현 승인): 플레이어 기본 능력치(최대 HP·이동 속도·복귀 속도, 이동 속도 초기값 6)를 DataSet으로 옮기고(CombatCore-V11-F14), V11-F07 몬스터 수치(HP·공격력·공격 간격, 몬스터마다 고유 id 한 행, 빈 칸은 기본값)를 DataSet으로 옮긴다. 현재 값을 그대로 옮기며 수치는 바꾸지 않는다. 기본 공격 피해는 기존 AttackSkillData에 둔다. 몬스터 점프 시간·높이는 6단계, Pos2 경계·앵커 간격 이동은 이후로 미룬다. 이 표는 최종 능력치 = DataSet 기본값 + 강화 보정 중 기본값만 담으며, 5단계 강화 표와 6단계 몬스터 표 구조의 기반이 된다.
- 네이티브 공격·피격 파이프라인과 HP 단일 적용 경계는 유지한다. 새 전투 규칙에 필요한 변경만 수행한다.

### 3: 전투 결과·정산 경계

- 현재 상대 1개체를 전제로 방별 상대 종류·보스 배정, 플레이어/상대 동시 전투 불능의 우선순위와 사망 시 처치 경험치 지급 범위를 정한다. 이 승패·정산 구현은 2단계에 포함하지 않는다.
- 전투 종료 정산과 Run 결과를 구분한다. Run 결과에서는 이미 정산한 경험치를 다시 지급하지 않는다.
- Level·EXP·보상 데이터의 소유권과 정산 식별자를 정해 4~5단계가 같은 결과를 사용하게 한다. 영구 저장 전체는 5단계에서 연결한다.

### 4: 최소 Run을 끝까지 연결

- Stage는 `탐험×3 → 상점 → 중간보스 → 탐험×3 → 상점 → 최종보스`다. 탐험 카드 후보는 전투·보물·안식처이며, 같은 종류는 카드 3장 안에서 최대 2장까지다.
- `암전 → 방 준비·중앙 배치 → 화면 밝힘 → 방 UI` 순서와 중복 선택·입장 차단을 연결한다.
- 전투 공간 참조와 1인 Run 격리 방식을 상세 계획에서 결정한다. 1인 게임이라는 이유로 서버 월드에 접속자가 항상 한 명이라고 가정하지 않는다.
- 대표 콘텐츠와 최소 보상·구매·회복 흐름으로 한 판을 먼저 완성한다. 전체 상품·장비·강화·영구 저장과 연동하는 작업은 5단계, 종류·수량 확대는 6단계(헤네시스 견본)와 8단계(2번 마을부터 데이터 행)가 담당한다.

### 5: 유지·소멸 규칙을 저장에 반영

- 일반 드롭·제작 장비의 유지 범위, 실패 보상, 제작·강화 비용·성공 규칙, 스킬 포인트 지급, 전투 중 장비·스킬 교체 허용 여부를 확정한다.
- 4단계의 최소 정산·구매 흐름을 실제 재화·소유권·장비 효과와 연결한다. 임시 데이터가 영구 저장에 섞이지 않게 한다.
- 저장 실패·재접속·중복 요청을 포함해 확인한다. 상점·인벤토리·저장 등 표준 시스템은 구현 전에 MSWPackages 적용 가능성을 검토한다.
- 플레이어 강화 데이터(2026-11-03 사용자 요청)는 §1 데이터 원칙대로 나눈다. DataSet(정적 정의): 장비 정의, 대장간 제작 재료·메소, 강화(스타포스·잠재능력) 비용·성공 규칙·단계별 능력치 증가량, 스킬 강화 효과·필요 스킬 포인트, 레벨별 스킬 포인트 지급. DataStorage(플레이어별 결과): 보유 메소, 보유 장비와 강화 단계, 스킬 레벨, 보유·사용 스킬 포인트, 장착·스킬 슬롯 설정. 한 판 한정 강화는 Run 메모리에만 두고 저장하지 않는다.
- 5단계는 강화 표 구조(열)를 확정하고 헤네시스 검증에 필요한 견본 행만 넣는다. 전체 강화 단계·수치 행은 8단계에서 채운다.
- 합산 경계: 최종 능력치 = 2단계 회차 B의 DataSet 기본값 + 강화 보정이다. 강화 보정은 영구 보정(DataSet 정의를 DataStorage 보유 상태로 조회)과 한 판 한정 보정을 합한 것이다. 기본값 표에는 성장 결과를 쓰지 않는다. DataStorage에는 증가량 자체를 복사하지 않고 보유 상태만 둔다(planner 제안, 5단계 계획에서 확인). 합산은 서버에서 하고 기존 HP 단일 적용·판정 경계를 유지한다.
- 5단계 상세 계획에서 정할 미결정: 표 구성과 열, 견본 수치, 보정 결합 방식(더하기/곱하기·적용 순서·상한), 보정 대상 수치 범위(판정 창·피해 배율 포함 여부), 강화 실패 처리, 저장 키 구성(마을·Stage는 고유 id 기준, §1 확장 원칙).

### 6: 1번 마을 견본과 몬스터·드롭 표 구조

- 일반 몬스터 최소 2종은 마을의 콘텐츠 종류 수다. 각 전투의 현재 상대는 1개체로 고정한다. 보스 선정·드롭 목록과 확률·이벤트 수치를 정한다. 해금은 표 구조와 연결만 마련하고, 조건 값은 8단계 시작 전 결정 사항이다.
- 1번 마을(헤네시스) 최종보스는 머쉬맘으로 정했다(2026-11-03). 일반 몬스터 주황버섯·초록버섯과 중간보스는 이 단계에서 추가하며, 추가할 때 planner 질문 절차로 공격 구성을 확인한다. 아래 "주황버섯 점프"는 현재 상대(머쉬맘)의 점프를 뜻한다.
- 주황버섯 MonsterData·MonsterStatData·패턴 행은 6단계 일반 몬스터 추가 때(2026-11-06 사용자). 모델(키 orangemushroom)은 2단계 회차 C·C2에서 1배 정리·영어 이름 정리만 한다.
- 헤네시스를 8단계의 표준 견본으로 완성한다. 몬스터·드롭과 마을(목록·순서·해금 조건) DataSet 표 구조(열)를 이 단계에서 확정해, 다른 마을은 행 추가로 구성할 수 있게 한다(§1 확장 원칙).
- 몬스터 동작 일반화 검토: 몬스터 동작을 공통 유형(예: 점프형·돌진형·원거리형, 예시이며 확정 아님)으로 일반화하고, DataSet에서 유형을 선택하며 새 유형만 코드를 추가하는 방식을 검토한다. 주황버섯 점프의 시간/속도 정책과 접근·복귀·높이 데이터화 범위는 [MonsterCombat 검토 계획](Plans/MonsterCombat.md)에 따라 이 검토 안에서 결정한다. 지금 속도를 변경하지 않는다.
- 기존 주황버섯 설정·진단 주의사항은 [몬스터 검토 계획](Plans/MonsterCombat.md)에 통합했다. 속도 조절만으로 공격 예고·판정 가독성까지 완료했다고 판단하지 않는다.

### 7: 기초 완성도 검증

- 헤네시스 견본 하나로 1~6단계 기초가 실제 기기·저장·반복 플레이에서 성립하는지 확인하고, 9단계 비교용 성능 기준값을 남긴다.
- 출시 여부는 판단하지 않는다. 배포 환경·장시간 반복 플레이·공개 전 필수 결함 해소는 9단계 완료 기준이다.

### 8: 콘텐츠 데이터 제작

- 선행 조건: 7단계 기초 검증, 5·6단계에서 확정한 강화·몬스터·드롭·마을 표 구조, 아래 결정 사항.
- 8단계 시작 전 결정 사항(모두 사용자 결정 미정, 2026-11-03 사용자 지시로 이곳에 모음, [GameDesign §8](GameDesign.md#8-추가-확정할-규칙)과 연결). 결정 전에는 임의로 정하지 않는다.
  1. 첫 출시에 포함할 마을 수: 첫 출시 컷라인이다. 8단계를 몇 번 마을까지 채운 뒤 9단계로 갈지만 정하며, 마을을 계속 추가하는 구조를 막는 결정이 아니다(§1 확장 원칙).
  2. 마을 해금 조건 값: 6단계에서 마련한 해금 표 구조에 넣을 실제 조건 유형·값.
  3. 에셋 목록(AssetList.md) 위치: 첫 에셋 작업 회차가 제안 위치에 잠정으로 만든 목록의 최종 위치(§1 에셋 목록). 바뀌면 그때 옮긴다.
- 2번 마을부터 마을 하나를 작업 단위로 상세 계획을 하나씩 작성한다. 2번 마을 이후의 이름·테마·몬스터 구성은 그 계획에서 정하며 지금 확정하지 않는다.
- 확정된 표 구조에 행을 채우는 것이 원칙이며 코드를 바꾸지 않는다. 6단계 공통 유형으로 표현할 수 없는 새 동작 유형만 예외로 코드를 추가하고, 그 범위를 마을 계획에 따로 적는다. 표에 열을 추가하는 것은 허용하며(기본값 원칙은 §1 확장 원칙), 추가 범위를 그 마을 계획에 적는다. 기존 열의 의미 변경·이름 변경·삭제는 기존 마을 영향과 함께 사용자 판단을 받는다.
- 몬스터·보스를 추가할 때마다 planner 질문 절차(난이도 위치, 공격 동작과 기존 애니메이션 선택, 공격별 속성·대응 유형·범위 칸 수·출현 비중)를 마을마다 적용하고 사용자 확인을 받는다. 기존 패턴 표를 복사하지 않는다.
- 몬스터·보스 에셋 절차(2026-11-03 사용자 확인): 마을마다 MSW 리소스(msw-search)에서 후보를 찾고, 후보와 사용 가능한 애니메이션 목록을 사용자에게 보여 선택받는다. 선택 뒤 머쉬맘처럼 ModelBuilder로 .model을 만들고 DataSet 행을 채운다. 절차 견본은 [Plan §18](Plans/2_CombatCore.md)(머쉬맘 리소스 교체·이름 변경)이다.
- 몬스터 외 에셋(배경·맵, NPC, 장비·아이템 아이콘, UI 이미지, 이펙트·사운드 등)도 마을마다 찾는다. 적합한 리소스가 없으면 사용자 제공 또는 msw-painter 직접 제작을 사용자에게 묻는다. 사용한 에셋은 에셋 목록에 기록하고, 임시·대체 에셋은 확정 전까지 목록에 남긴다.
- 강화 단계·수치 행도 이 단계에서 채운다. 플레이어별 결과의 DataStorage 구조는 5단계 것을 그대로 쓴다.
- 1:1 현재 상대 고정과 단일 소유권을 유지한다. 마을 수가 늘어도 범용 다중 대상 전투 체계를 만들지 않는다.

### 9: 출시 검증과 첫 출시 범위

- 선행 조건: 첫 출시 범위 콘텐츠 완성(컷라인까지 8단계 완료). 출시 범위의 에셋이 모두 확정되고 임시 에셋이 0이어야 한다. 9단계 전에 게임은 완성돼 있어야 한다(2026-11-03 사용자 확인). 이 "완성"은 첫 출시 컷라인까지의 마을 콘텐츠 완성을 뜻하며 마을 추가가 끝났다는 뜻이 아니다(§1 확장 원칙).
- 기존 7단계의 출시 관련 완료 기준(실제 기기·배포 환경·장시간 반복 플레이·공개 전 필수 결함)을 출시 대상 전체 콘텐츠에 적용한다.
- 첫 출시에 포함할 마을 수(컷라인)는 [8단계 시작 전 결정 사항](#8-콘텐츠-데이터-제작)이다.
- 출시 뒤에 추가하는 마을은 8단계로 만들고, 공개 전에 9단계 필수 확인을 변경 범위에 다시 적용한다. 이 반복이 마을을 지속적으로 출시하는 방식이다(§1 확장 원칙).

## 5. 문서 운영과 단계 전환

팀의 역할·승인·공유 파일/Maker 사용·인계는 [ChatRoles 팀 운영 규칙](../ChatRoles/README.md)을 따른다. 현재 단계와 미완료 추적은 Engineering 문서에서 관리한다.

- 수정·리팩토링 단기 계획은 `Engineering/{TaskName}Plan.md`에 두고 완료 후 정리한다. 이 로드맵은 단기 실행 계획이 아니므로 개별 작업 종료 때 삭제하지 않는다.
- 단계 전환은 필수 완료 기준과 남은 확인을 검토한 뒤 결정한다. 미검증 범위를 넘겨 진행하려면 사용자 승인과 추적 위치를 남긴다. 문서 생성·소스 존재만으로 기능을 완료 처리하지 않는다.
